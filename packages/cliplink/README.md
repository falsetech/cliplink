The CLIPLINK room protocol: end-to-end encryption, the room wire types, and the
HTTP and WebSocket transports. Everything a client needs to talk to a CLIPLINK
room, with no framework and nothing browser-specific.

The [web app](../../) and the `cliplink` CLI are both built on this, so there is
one implementation of the encryption rather than one per surface.

```bash
npm install @thebkht/cliplink        # the library
npm install -g @thebkht/cliplink     # the `cliplink` command
```

The CLI ships in this package as the `cliplink` binary — see [CLI.md](./CLI.md).
Importing the library never loads it, so a browser bundle pays nothing for it.

Needs Node 22 or newer, for the `WebSocket` and Web Crypto globals. There are no
third-party dependencies: in a browser the library runs on the platform, and in
the terminal it runs on Node's own globals.

## Usage

```ts
import {
  createEncryptedTransport,
  createHttpClient,
  createWebSocketTransport,
  generateRoomKey,
} from "@thebkht/cliplink";

const options = { baseUrl: "https://cliplink.thebkht.com" };

// The key is generated here and never sent. The server is told only its
// fingerprint, which lets it tell a joiner their key is wrong.
const key = await generateRoomKey();
const { code } = await createHttpClient(options).createRoomRequest(key.check);

const transport = createEncryptedTransport(createWebSocketTransport(options));
transport.setRoomKey(code, key);

await transport.connect(code);
await transport.sendClip(code, { text: "hello", senderId: "abcdef" });
```

Outside a browser, supply a WebSocket:

```ts
import WebSocket from "ws";

const options = {
  baseUrl: "https://cliplink.thebkht.com",
  WebSocket: WebSocket as unknown as typeof globalThis.WebSocket,
};
```

`baseUrl` may be a function, resolved per call. That is what lets a browser
transport be constructed at module scope, where server rendering evaluates the
module before `window.location` exists.

## What it contains

| | |
| --- | --- |
| `crypto` | AES-GCM-256 with HKDF-derived subkeys for clips and signaling, Crockford base32 keys, and a one-way fingerprint the server may hold |
| `encrypted-transport` | Wraps a wire transport so everything above it works in plaintext |
| `http` / `ws` | The room REST API and the realtime socket, bound to an origin |
| `validation` | The wire's own rules — room codes, ciphertext shape, peer ids, signal payloads |
| `protocol` | The limits that two clients must agree on |
| `room-code` / `qr` | Room links, with the key in the fragment, and a QR encoder for them |

## Encryption

A room key is 32 random bytes, generated by the client. HKDF derives a clip
key, a signaling key, and an 8-byte fingerprint from it. The fingerprint is
one-way, so the server can hold it and be no closer to the key.

Every payload is `v1.` followed by base64url of a 12-byte nonce and the AES-GCM
ciphertext. The room code is the additional authenticated data, so a ciphertext
lifted out of one room cannot be replayed into another.

The key travels in a URL fragment, which browsers never send to a server. That
is the whole reason the encryption is end-to-end rather than merely at rest.

`deriveOpenRoomKey` is the deliberate exception: it derives a key from the room
code, so the code alone opens the room. The server sees the code, so this is
**not** end-to-end. What it buys is one wire format instead of two.

## Compatibility

Wire protocol v1. A browser tab loaded before a deploy keeps talking to one
loaded after it, so the format is fixed: the test suite pins ciphertexts from
earlier builds and a change that cannot open them is a breaking change.
